## 2. What the application does

TKIA Solver is a web PWA used as an interactive case-solving board for the book puzzle "The Killer Isn't Alice".

The application helps the user:
- track clues
- track findings
- eliminate pages and chapters
- maintain candidate killer pages
- inspect pages and chapters
- verify suspect names
- track checked pages/chapters
- determine what work remains
- recommend the next most valuable investigation step
- preserve and restore case state

The application is intended to work well on iPad.

## 6. Clue rules

There are 18 clues.

These rules are authoritative.

### Clue 1
Names with 3 letters or fewer are eliminated.

### Clue 2
The killer's first initial cannot be S.

### Clue 3
Count vowels A/E/I/O/U.
Y is not a vowel.
Repeated vowels count separately.

### Clue 4
The same exact spelling must appear at least twice on one numbered page.

### Clue 5
A consecutive repeated letter eliminates a name.

### Clue 6
Anna and Zack each appear once.
The killer page is strictly between Anna and Zack.

If one of the two locations is unknown, do not invent the possible range.

### Clue 7
Names exactly 6 letters long are eliminated.

### Clue 8
The killer name cannot contain X, Y, or Z.

### Clue 9
A three-letter name can be on the same, previous, or next page.
The count continues across chapter boundaries when necessary.
It must be no more than 10 names away from the killer in normal reading order.

Do not assume that "10 names" equals "10 pages".

### Clue 10
The first name in the main body must share a letter with the killer.

Book titles and chapter titles are ignored.

### Clue 11
Count every name beginning with M, including duplicates.
The killer page must contain fewer than 3 such names.

### Clue 12
A Kardashian must appear on the killer's page or within 4 pages before/after it.
The killer's own page counts.

### Clue 13
Count only names in the main text, including duplicates.
Titles are excluded.
The killer page must contain an even number of names.

### Clue 14
The physical facing page must contain a qualifying President first name.

Examples:
- page 2 faces page 3
- page 4 faces page 5

### Clue 15
The chapter containing the killer must have a widely accepted city in its title.

A city can count even when the same word has another meaning in the chapter title.

### Clue 16
Sasha must appear on the killer page or exactly one page before/after.

### Clue 17
The chapter containing the killer must contain all four Beatles.

### Clue 18
Final killer decision.

## 7. Important conceptual distinction

There is a critical distinction between:

Impact Unit
and
Work Scope.

Impact Unit:
The smallest unit a clue can directly eliminate or affect.

For the page-level logic, this is usually a page.

Work Scope:
The actual amount of book work required to obtain the information.

A clue may affect one page at a time but still require scanning 100+ candidate pages.

Therefore:

Do NOT estimate effort simply from the size of the impact unit.

Example:
Clue 4 can eliminate one page at a time, but if 150 candidate pages remain unchecked for Clue 4, completing that investigation may require scanning approximately 150 pages.

## 8. Candidate pages

The application maintains a set of currently possible killer pages.

Candidate-page logic is derived from:
- page findings
- chapter findings
- completed clue constraints
- other case state

Candidate pages are derived state.

Do not store derived candidate status as permanent case data unless explicitly instructed.

## 9. Findings and validation

Findings have dependencies and validation logic.

Be especially careful with:

activeFindings()
refreshFindingStatuses()
validateFinding()
validateFindingDependency()
clueUnitNeedsAction()
clueUnitRelevance()
clueRelevantPageSet()
killerPossibleOnPage()

Historically, these functions created expensive recursive/circular calculation paths.

A previous restore bug caused a stack overflow because finding validation and candidate-page calculation recursively triggered each other.

That bug was fixed.

Do not casually introduce new calls from read-only analysis functions into refreshFindingStatuses().

Prefer:
- explicit data passed into calculations
- per-analysis derived state
- clearly bounded calculations

Avoid:
- hidden mutation from read helpers
- validation triggered repeatedly inside page loops
- global refreshes inside candidate-page calculations

## 10. Dynamic "What should I check next?"

The application has a dynamic investigation recommendation feature.

The feature should NOT simply follow a fixed SOLUTION_ORDER.

It should rank currently useful investigation actions according to their solving value relative to the work required.

The ranking is a heuristic prioritization system.

It is NOT:
- a probability of the killer being on a page
- a guaranteed optimal strategy
- a statistically validated expected-value model

Do not describe heuristic scores as probabilities.

## 11. Dynamic solver principles

The dynamic solver should consider:

- elimination potential
- information gained
- ability to unlock other reasoning
- certainty / confidence
- current candidate coverage
- actual work required

Do not multiply these dimensions together blindly.

Work/effort should be treated explicitly.

Unknown information must remain unknown.

Do not convert missing information into zero or assume a favorable value.

When the impact of a clue cannot yet be calculated because information is missing, use value-of-information reasoning.

### Clue 6 example

If Anna's page is known but Zack's page is unknown:

Do not invent a range.
Do not calculate an elimination percentage from an assumed Zack location.

The useful action may instead be finding Zack.

Once Anna and Zack are known, the range can be calculated directly.

## 13. Work-scope principles

Work scope must reflect actual investigation effort.

Examples:

Clue 4:
Potentially scan each remaining candidate page.

Clue 11:
Potentially scan each remaining candidate page.

Clue 12:
Potentially scan the union of pages within ±4 pages of candidate pages.

Clue 14:
Potentially inspect the unique physical opposite pages of candidate pages.

Clue 15:
Potentially inspect the titles of relevant candidate chapters.

Clue 17:
Potentially inspect the content of relevant candidate chapters.

Clue 16:
Potentially scan the union of candidate neighborhoods within ±1 page.

Clue 9:
The ten-name reading-order window cannot safely be inferred from page numbers alone.
Do not equate ten names with ten pages.

If exact text-level name positions are unavailable, use a conservative scope rather than pretending the exact scope is known.

## 14. Clue 9 warning

There is currently a known conceptual consistency issue around Clue 9.

Its conservative work scope may cover the entire active case range because page numbers alone do not reveal a ten-name reading-order window.

Its relevance calculation must not incorrectly assume that candidate pages plus only one adjacent page fully represents the ten-name window.

Do not change this behavior casually.

If addressing it, explicitly reconcile:
- reading-order distance
- page boundaries
- chapter boundaries
- actual name positions

before changing the algorithm.

## 15. Performance principles

The application must work well on iPad.

Avoid:
- repeated full-page scans
- repeated full-finding validation
- nested page × finding × page calculations where avoidable
- triggering refreshFindingStatuses() from every page calculation
- unnecessary DOM rendering
- hidden recursion
- repeated calculation of identical derived state during one analysis pass

Within one analysis pass, derived information may be reused safely.

Long-lived caches require reliable invalidation after:
- findings change
- clues change
- checked pages change
- checked chapters change
- restore
- migration
- relevant case-state changes

Prefer short-lived per-analysis caching when possible.

## 16. Important historical performance bug

The dynamic "What should I check next?" feature became extremely slow because candidate construction could repeatedly call finding validation.

The cause involved duplicate killerPossibleOnPage() implementations.

The intended architecture is:

nextChecks()
→ withPageAnalysis()
→ candidate construction using an explicit findings snapshot
→ rankedSolutionClues()
→ solutionValueModel()

Candidate construction must not trigger a complete finding-status refresh for every page.

## 17. Important historical restore bug

Backup restore previously caused recursive validation and stack overflow.

The fix introduced a validation guard and careful handling of active findings.

Do not remove the validation guard without proving that the full dependency graph remains safe.
